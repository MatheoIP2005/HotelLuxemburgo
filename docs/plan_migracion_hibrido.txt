1. PRINCIPIO DE LA ARQUITECTURA HÍBRIDA
================================================================================

La arquitectura adopta un modelo donde REST gobierna la frontera pública del
sistema y gRPC gobierna la comunicación interna entre microservicios. Esta
separación no es opcional: responde a dos restricciones irreconciliables con
un único protocolo.

Regla de oro:
  • Si el endpoint es llamado por el cliente, browser o frontend React
    → REST (público, sin autenticación o con JWT visible)
  • Si el endpoint es llamado exclusivamente por otro microservicio
    → gRPC (interno, tipado, HTTP/2)
  • Si el endpoint es llamado por ambos (ej. admin REST + servicio interno)
    → mantener REST interno + implementar equivalente gRPC

Canal                           | Protocolo         | Autenticación                    | Propósito
Cliente / Browser → Gateway     | REST / HTTPS      | JWT Bearer                       | Contrato público estable
Servicio → Servicio (interno)   | gRPC / HTTP2      | mTLS (académico: cleartext)      | Rendimiento, tipado estricto
Eventos de auditoría            | gRPC fire-forget  | Sin respuesta bloqueante         | Trazabilidad sin latencia

3. CRITERIO DE DECISIÓN: QUÉ CAMBIA A gRPC Y QUÉ SE MANTIENE REST
================================================================================

No todos los endpoints internos migran a gRPC. La migración aplica cuando el
endpoint es invocado exclusivamente por otro servicio en un flujo transaccional
o de validación. Los endpoints administrativos de lectura permanecen como REST.

[MIGRAN A gRPC]
  • ValidateToken (auth)
    - REST actual: No existía como REST interno
    - Razón: Todos los servicios validan JWT en cada request; latencia crítica

  • CheckAvailability (accommodation)
    - REST actual: GET /habitaciones/disponibilidad
    - Razón: Llamado por reservation-service en cada confirmación; real-time

  • ConfirmRoomLock (accommodation)
    - REST actual: PATCH /habitaciones/{id}/estado
    - Razón: Solo reservation-service lo llama; bloqueo atómico

  • UpdateRoomStatus / check-in-out (accommodation)
    - REST actual: PATCH /habitaciones/{id}/estado
    - Razón: Solo stay-service lo llama al hacer check-in / check-out

  • GenerateReservationInvoice (billing)
    - REST actual: POST /facturas (REST privado)
    - Razón: Solo reservation-service genera facturas; eliminar acceso REST

  • GenerateFinalInvoice (billing)
    - REST actual: POST /facturas/final (REST privado)
    - Razón: Solo stay-service al hacer checkout

  • UpdateInvoiceBalance / MarkInvoicePaid (billing)
    - REST actual: No existía explícito
    - Razón: payment-service actualiza saldo; nunca expuesto al cliente

  • ValidateStayCompleted (stay)
    - REST actual: No existía
    - Razón: rating-service verifica estadía antes de aceptar valoración

  • EmitAuditEvent (audit)
    - REST actual: No existía
    - Razón: Fire-and-forget desde todos los servicios; no bloquea flujo

[SE MANTIENEN REST]
  • GET /api/v1/accommodations/** (búsqueda pública)
    - Razón: Consumido por browser / frontend; no tiene equivalente gRPC

  • POST /api/v1/internal/auth/login-refresh-logout
    - Razón: Frontend llama login; gRPC solo para ValidateToken inter-servicio

  • GET/POST /api/v1/public/reservas
    - Razón: El cliente crea reservas vía Gateway; interfaz de usuario

  • PATCH reservas/{id}/confirmar - cancelar
    - Razón: Operación admin via Gateway; internamente orquesta gRPC

  • GET /internal/facturas, /estadias, /pagos (lectura admin)
    - Razón: Lectura administrativa via Gateway; no hay ganancia con gRPC

  • GET /accommodations/{guid}/reviews
    - Razón: Consumido por browser; rating-service usa gRPC solo para validar estadía


4. DEFINICIÓN DE .PROTO FILES POR MICROSERVICIO
================================================================================

Los archivos .proto son el contrato de comunicación interno. Deben vivir en un
repositorio compartido (/protos/) y compilarse como paquete NuGet referenciado
por todos los servicios. Jose Daniel es el responsable de mantener este repo.

--- 4.1 auth.proto ---
  ValidateToken
    Request:  ValidateTokenRequest { string token }
    Response: ValidateTokenResponse { bool valid; string user_guid; repeated string roles; }

  GetUserRoles
    Request:  GetUserRolesRequest { string user_guid }
    Response: GetUserRolesResponse { repeated string roles; }

--- 4.2 accommodation.proto ---
  CheckAvailability
    Request:  CheckAvailRequest { string sucursal_guid; string fecha_entrada; string fecha_salida; int32 cantidad_personas; }
    Response: CheckAvailResponse { bool disponible; repeated HabitacionDisponible habitaciones; }

  ConfirmRoomLock
    Request:  ConfirmLockRequest { string habitacion_guid; string reserva_guid; string fecha_entrada; string fecha_salida; }
    Response: ConfirmLockResponse { bool success; string mensaje; }

  UpdateRoomStatus
    Request:  UpdateRoomStatusRequest { string habitacion_guid; string nuevo_estado; string operacion_guid; }
    Response: UpdateRoomStatusResponse { bool success; }

  ReleaseRoomLock
    Request:  ReleaseRoomRequest { string habitacion_guid; string reserva_guid; }
    Response: ReleaseRoomResponse { bool success; }

--- 4.3 reservation.proto ---
  GetReservation
    Request:  GetReservationRequest { string reserva_guid }
    Response: GetReservationResponse { string reserva_guid; string estado; string cliente_guid; }

  ValidateReservationForCheckin
    Request:  ValidateCheckinRequest { string reserva_guid }
    Response: ValidateCheckinResponse { bool valid; string cliente_guid; repeated string habitacion_guids; }

--- 4.4 stay.proto ---
  ValidateStayCompleted
    Request:  ValidateStayRequest { string estadia_guid }
    Response: ValidateStayResponse { bool completed; string reserva_guid; }

  GetStayStatus
    Request:  GetStayStatusRequest { string estadia_guid }
    Response: GetStayStatusResponse { string estado; string cliente_guid; }

--- 4.5 billing.proto ---
  GenerateReservationInvoice
    Request:  GenReservInvoiceRequest { string reserva_guid; repeated InvoiceLineItem items; }
    Response: GenInvoiceResponse { string factura_guid; decimal total; }

  GenerateFinalInvoice
    Request:  GenFinalInvoiceRequest { string reserva_guid; string estadia_guid; }
    Response: GenInvoiceResponse { string factura_guid; decimal total; }

  UpdateInvoiceBalance
    Request:  UpdateBalanceRequest { string factura_guid; decimal monto_pagado; }
    Response: UpdateBalanceResponse { decimal saldo_pendiente; }

  MarkInvoicePaid
    Request:  MarkPaidRequest { string factura_guid }
    Response: MarkPaidResponse { bool success; }

--- 4.6 audit.proto (fire-and-forget) ---
  EmitAuditEvent
    Request:  AuditEventRequest { string servicio_origen; string tabla_afectada; string operacion; string entidad_guid; string usuario_guid; string detalle_json; }
    Response: google.protobuf.Empty

7. DEFINITION OF DONE — CHECKLIST POR MICROSERVICIO
================================================================================

Un microservicio se considera Done cuando cumple TODOS los siguientes criterios:

  [ ] Levanta en Docker sin errores (docker-compose up)
  [ ] Todos sus endpoints REST retornan el código HTTP correcto
  [ ] Sus métodos gRPC responden correctamente (grpcurl o test unitario)
  [ ] Emite eventos a audit-service en cada operación CRUD
  [ ] Valida JWT via auth-service.ValidateToken en endpoints protegidos
  [ ] Al menos 5 tests unitarios en capa Application/Business
  [ ] README.md con instrucciones de ejecución local
  [ ] PR aprobado por al menos 1 compañero de equipo
